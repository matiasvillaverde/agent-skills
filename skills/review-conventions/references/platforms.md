# Platform-specific naming and enforcement

Read only the active platform. These are starting points, not a substitute for the repository's
owner, pinned tools, existing public contracts and legitimate exceptions. Tool docs can describe
versions newer than the installed tool. Formatting and naming are different checks.

| Platform | Naming questions with practical value | Existing enforcement to inspect |
| --- | --- | --- |
| Swift | Judge call-site clarity, argument labels, side effects and domain terms. Preserve protocol/override/Objective-C selectors, Codable mappings and resource names. The [Swift API guidelines](https://www.swift.org/documentation/api-design-guidelines/) prioritize clear usage over fewer characters. | Existing swift-format/SwiftLint configuration and SourceKit/SwiftSyntax tooling. [SwiftLint `identifier_name`](https://realm.github.io/SwiftLint/identifier_name.html) is a configurable style rule, not an autocorrecting semantic review. Its length defaults are not universal quality thresholds. |
| Rust | Types/traits versus values/modules have different casing. Conversion names express cost and ownership; read signatures and behavior before judging `as_`, `to_` or `into_`. Preserve public paths, macros and serde names. [API naming guidance](https://rust-lang.github.io/api-guidelines/naming.html). | Compiler naming diagnostics and selected existing Clippy rules. [Clippy categories](https://doc.rust-lang.org/clippy/lints.html) distinguish subjective style from correctness; do not enable every pedantic/restriction lint to audit names. |
| Go | Exported capitalization changes visibility. Read the full package-qualified name to avoid stuttering; package names and filesystem names have different roles. Preserve build suffixes/tags, JSON tags and interface methods. [Effective Go naming](https://go.dev/doc/effective_go#names) remains useful core-language guidance, but its 2009 document is not an up-to-date modules/generics guide. | `gofmt` handles formatting, not semantic naming. Inspect existing diagnostics and gopls. A genuinely needed custom analyzer can use [go/analysis](https://pkg.go.dev/golang.org/x/tools/go/analysis) with syntax and type information. |
| TypeScript/JavaScript | Separate values/types, components/hooks, framework-reserved paths and external property names. Prefer the actual project's conventions; [Google's guide](https://google.github.io/styleguide/tsguide.html#naming) explicitly warns that its environment-specific policies may not apply elsewhere. | Existing ESLint and TypeScript project context. [`naming-convention`](https://typescript-eslint.io/rules/naming-convention/) supports selectors/exceptions and warns against overly strict enforcement. Do not impose interface prefixes, constant casing or private-field policies universally. |
| Python | PEP 8 provides class/function/module conventions while explicitly prioritizing local consistency and backward compatibility. Respect protocol methods, subclass overrides, keyword arguments, `__all__`, serialized fields and import names. [PEP 8](https://peps.python.org/pep-0008/#naming-conventions). | Existing Ruff/other configured checks; [Ruff's naming rules](https://docs.astral.sh/ruff/rules/#pep8-naming-n) cover specific syntax, not domain meaning. An installed API can have consumers absent from the checkout. |
| Zig | Names depend on role: types and type-producing functions, ordinary callables, values, and namespace-like structs differ. A field-bearing file and a namespace file can intentionally use different casing. Read the exact version's [style guidance (0.17.1 example)](https://ziglang.org/documentation/0.17.1/#Names), which allows meaningful established exceptions. | Existing `zig fmt`, compiler and selected ZLS/AST tooling. Do not pretend the formatter proves all naming policy or mechanically rename imported C symbols. |
| C/C++/CUDA | Follow the owning project for types/functions/files, public headers and macro names. Do not confuse its house style with a language requirement. Retain imported library style and C/ABI/exported names. [C++ Core Guidelines NL.8](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#nl8-use-a-consistent-naming-style). | Existing clang-format and clang-tidy with the real compile database. [`readability-identifier-naming`](https://clang.llvm.org/extra/clang-tidy/checks/readability/identifier-naming.html) has per-kind rules; an empty configuration checks nothing. Virtual naming is diagnosed at the base declaration because overrides cannot be fixed independently. Preserve CUDA compilation context. |

Use semantic rename tooling when available and appropriate, then verify consumers. None of these
tools establishes that a domain term is honest, that a protocol name may safely change or that
all platforms were analyzed. Do not introduce new language-wide standards during a scoped audit.
