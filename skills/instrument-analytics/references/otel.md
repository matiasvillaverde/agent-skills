# OpenTelemetry boundaries for product analytics

Evidence checked 2026-11-13 against OpenTelemetry specification 1.62.0, OTLP 1.11.1, and CloudEvents 1.0.2. Pin the project's actual SDK, exporter, instrumentation, and semantic-convention versions: protocol stability does not imply identical support in every language. GenAI conventions moved into a separate repository and remain Development; inspect individual definitions before adopting them. [OTel specification](https://opentelemetry.io/docs/specs/otel/), [Language status](https://opentelemetry.io/docs/languages/), [GenAI status](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/README.md)

Keep the product-event contract application-owned: a small boundary names meaningful outcomes and supplies allowlisted properties to the selected analytics adapter. Emit from an existing application boundary or established domain-event consumer, deriving facts from completed outcomes without duplicating business rules. Keep vendor delivery, consent, filtering, and schema mapping outside core business logic. Use OpenTelemetry's tracing API directly at operation boundaries instead of building a parallel tracer abstraction. Libraries depend on the API; application startup owns the SDK and exporters. This boundary design is our recommendation, supported by OTel's API/SDK separation. [Client architecture](https://opentelemetry.io/docs/specs/otel/overview/)

Reuse existing providers and automatic instrumentation; avoid recording the same HTTP/database work twice. Configure resource identity, service version, and deployment environment once; use instrumentation scope for the emitting library/module and its version. Request, user, and run identifiers belong on selected records, not as service resources or unbounded metric dimensions. Configure batching, sampling, export limits, and shutdown in the application. Export through OTLP directly to a compatible backend or through an existing Collector when its processing/routing is useful; no universal Collector requirement. [Resources](https://opentelemetry.io/docs/specs/otel/resource/sdk/), [Service conventions](https://opentelemetry.io/docs/specs/semconv/resource/service/), [Exporters](https://opentelemetry.io/docs/concepts/signals/traces/)

Propagate W3C `traceparent` and `tracestate` through the supported propagator and actual asynchronous context mechanism. Restore/detach scopes correctly, and end spans on success, error, cancellation, and stream termination. Use parent/child relationships for contained work; use links for causal relationships such as batches, fan-in, or deferred work when a single parent is misleading. Links known at creation can influence head sampling; links added later cannot retroactively change that decision. A trace identifier provides correlation, not authorization or business-event identity. [Trace Context](https://www.w3.org/TR/trace-context/), [OTel context](https://opentelemetry.io/docs/specs/otel/context/), [Tracing API](https://opentelemetry.io/docs/specs/otel/trace/api/)

Treat incoming propagation as untrusted. Baggage has no built-in integrity protection and can leave the service through automatic instrumentation. Allowlist necessary bounded values, remove private data before recording, and control propagation across external boundaries. Never derive authorization from baggage. It is separate from span/log/metric attributes unless explicitly copied. Trace Context is a W3C Recommendation; published Baggage is still a Candidate Recommendation Snapshot. [W3C Baggage](https://www.w3.org/TR/baggage/), [OTel baggage security](https://opentelemetry.io/docs/concepts/signals/baggage/)

Record business counters independently of trace sampling; sampled spans and span events cannot establish complete conversion totals. Exemplars connect selected measurements to traces without making every measurement a trace. Avoid identifiers as metric labels. Removing an attribute through a metric View does not reliably redact it: exemplars can retain excluded attributes. Sanitize at the instrumentation boundary or configure exemplars accordingly. Even unsampled metrics remain telemetry, not a transaction ledger. [Metrics SDK](https://opentelemetry.io/docs/specs/otel/metrics/sdk/)

Bound export queues, retries, bytes, and deadlines; expose rejected/dropped data and shutdown failures. A batch processor can drop spans when full. OTLP acknowledgments cover one client/server hop; retries can duplicate data, and successful export does not prove durable end-to-end receipt. Required business events need their own explicit persistence and deduplication contract; use an existing durable event path when that requirement exists. [Tracing SDK](https://opentelemetry.io/docs/specs/otel/trace/sdk/), [OTLP delivery](https://opentelemetry.io/docs/specs/otlp/)

CloudEvents is optional interoperability packaging, useful when multiple independent consumers need a common envelope. Its required `specversion`, `type`, `source`, and `id` describe an event; `source` plus `id` identifies duplicates. It supplies neither product semantics nor exactly-once delivery. Preserve an event's identity on resend, keep correlation distinct, and avoid wrapping every internal analytics call without an interoperability need. Verify exported fields, context continuity, disabled instrumentation, sampling-independent counters, and unavailable-sink behavior on the changed path. [CloudEvents stable specification](https://github.com/cloudevents/spec/blob/ce@stable/cloudevents/spec.md)
