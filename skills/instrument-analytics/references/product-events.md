# Product analytics: meaning before instrumentation

Begin with the decision, not an event catalog. Read existing product goals, instrumentation, dashboards and privacy settings. For each proposed addition, connect the question, intended decision, population, event or authoritative data source, and owner. Reuse the current tracking contract; write only the delta needed for this feature. Keep an event only when its information changes an analysis or action. There is no universal event count. [Decision-first guidance](https://github.com/coreyhaines31/marketingskills/blob/1f837447b20bb6f0e72d87b80ece1c221c362c7d/skills/analytics/SKILL.md#L27)

Define metrics before emitting their ingredients. Activation means a specific delivered value within a stated window after cohort entry. Funnel conversion divides qualifying completions by eligible entrants, with identity unit, order, retries/reentry, exclusions and conversion window stated. Retention needs a cohort-entry event, meaningful return action, interval and exact-versus-on-or-after definition. Distinguish calendar from elapsed-time windows. Report only mature windows as final; show pending cohorts and late-arrival cutoff separately. Apply consistent internal/test/bot exclusions to numerator and denominator. Document consent-related missingness rather than calling the observable population all users. [Funnels](https://docs.mixpanel.com/docs/reports/funnels/funnels-advanced), [retention](https://docs.mixpanel.com/docs/reports/retention)

Emit success where the authoritative operation commits or its durable outcome is known. A click, optimistic UI, request acceptance or success-page revisit does not prove completion. Record intent separately only when abandonment or failure matters, and relate attempts to outcomes without counting retries as new success. Choose one producer for each logical fact. Derive inventory, entitlements and financial truth from their owning systems; lossy product analytics must not become those authorities. Use an existing durable event/outbox when appropriate; a dashboard alone does not justify introducing one. [Canonical emission](https://github.com/Accoil/product-tracking-skills/blob/91ae6a6267804e83a792b477f348d00c51d1a6cf/skills/product-tracking-design-tracking-plan/references/common-mistakes.md#L208)

For retryable delivery, retain a stable logical-event identifier, occurrence time and correctly scoped identity across attempts. Separate event time from received time. Bound offline storage, retry duration and shutdown work; define expiry and late/backfill handling. Do not relabel queued events with whoever logs in next. Verify the provider's actual deduplication keys, retention window and acceptance semantics: Amplitude's documented rule is bounded, not unlimited exactly-once delivery. Reconcile missing/duplicate critical outcomes against their source. [Deduplication](https://amplitude.com/docs/apis/analytics/http-v2), [retry behavior](https://amplitude.com/docs/apis/analytics/http-api-batching-retries)

Keep integration small. Prefer existing typed events or a tiny provider adapter at the application boundary; keep provider setup, mapping, consent and delivery out of domain calculations and rendering loops. Call it with already-known outcomes and allowlisted context; do not duplicate business rules to infer success. Analytics failure must not fail the user action. Add no CDP, generic bus, parallel YAML registry or code generation unless a demonstrated need justifies it. One name with a meaningful variant property can simplify queries, but reducing event-name cardinality does not inherently reduce emitted volume. [Small interface guidance](https://github.com/clamp-sh/analytics-skills/blob/b9e06c5131a6060114e68893bc34fc77b65a9552/skills/event-schema-author/SKILL.md#L167)

Preserve established names, units and meanings. Prefer compatible additions; coordinate breaking changes with queries, dashboards and mixed-version clients. Missing required data is a defect until the intended contract says otherwise. No recent observation is insufficient evidence to delete a rare event. Current-state snapshots need source, timestamp and freshness; reuse an existing query or synchronization path instead of automatically scheduling another job.

Distinguish event-time context from mutable profile traits. If the question is which plan a customer held when an action occurred, capture permitted plan-at-event context or join historical authoritative state; today's profile is not that answer. Define units, currency, timezone and null meaning. For important rates, calculate from the same qualifying rows and reconcile a second way; avoid averaging subgroup percentages without population weights.

Treat pseudonymous IDs, traits, URLs and joins as governed data. Use permitted stable identity; reset user/group context on logout or account change without losing consent choices. Anonymous-to-known merges require a verified identity and permitted purpose. Denied/withdrawn collection must follow the product's policy, including buffered data. Check installed SDK behavior and outgoing traffic: PostHog documents queued-event and feature-flag exceptions to opt-out. [Identity](https://posthog.com/docs/product-analytics/identify), [collection controls](https://posthog.com/docs/privacy/data-collection), [reset behavior](https://posthog.com/docs/references/posthog-js)

Verify consequential cases: committed success versus rollback, duplicate/retried delivery, offline arrival, consent changes and account switching. Use focused assertions for event meaning, identity and payload boundaries; inspect an actual allowed delivery and representative funnel query. Report what was verified and any coverage gap.
