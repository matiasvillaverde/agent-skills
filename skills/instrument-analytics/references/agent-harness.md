# Agent harness analytics

Begin with a decision: whether tasks complete correctly, why a run stalls, or where time and resources go. Reuse the harness's existing lifecycle hooks and telemetry. Instrument the run boundary, model operations, consequential tools, and retrieval; avoid every-token spans, duplicate auto/manual spans, and a new framework solely for analytics.

Treat business outcome separately from transport/model success. A 200 response, completed stream, or normal tool return does not establish that the requested task succeeded. Define a small application-owned outcome vocabulary, such as completed, partial, failed, cancelled, denied, and budget-exhausted, against observable acceptance criteria. Track human takeover where relevant. These are application semantics, not invented `gen_ai.*` conventions.

Use the conventions supported by the installed instrumentation and pin that version. The current [GenAI registry](https://github.com/open-telemetry/semantic-conventions-genai/tree/e6658f14c9d9ea0760825f029cb82e7673f48fab/docs/gen-ai) remains Development and has changed metric names. There is no universal requirement to enable the old `gen_ai_latest_experimental` flag. Verify emitted output before updating dashboards.

| Selected signal | Current convention or application measurement | Meaning |
| --- | --- | --- |
| Run outcome and latency | Application outcome count; `gen_ai.invoke_agent.duration`, histogram, seconds | Task result and end-to-end agent duration |
| Model latency | `gen_ai.client.inference.duration` and `.time_to_first_chunk`, histograms, seconds | Logical call and first substantive streamed output |
| Run work | `gen_ai.invoke_agent.inference_calls` / `.tool_calls`, histograms, `{inference_call}` / `{tool_call}` | Direct work per invocation |
| Token consumption | `gen_ai.client.inference.usage.input_tokens` / `.output_tokens`, counters, `{token}` | Known usage, including failed calls when available |
| Tool and retrieval time | `gen_ai.execute_tool.duration` / `gen_ai.retrieval.duration`, histograms, seconds | Dependency or pipeline latency |
| Wait and limits | Application queue/wait seconds; retry, denial, handoff and budget-exhaustion counts | Harness-specific causes of delay or non-completion |

For instrumentation adopting that pinned version, examples are local agent spans `invoke_agent {agent_name}` with INTERNAL kind, remote invocations CLIENT, model calls `chat {request_model}` with CLIENT kind, and tool execution `execute_tool {tool_name}` with INTERNAL kind. `invoke_workflow` covers application-directed control flow. Match kinds to the owned operation; an instrumented remote dependency may already supply its own CLIENT span. Do not rename or duplicate working spans merely to match newer examples. A logical model span includes automatic retries and lasts until completion, cancellation, or failure; streaming creation is not completion. Record first-chunk time only when meaningful output arrives, not on keep-alives. Preserve partial outcomes and known usage without inventing zero usage when unavailable. [Inference](https://github.com/open-telemetry/semantic-conventions-genai/blob/e6658f14c9d9ea0760825f029cb82e7673f48fab/docs/gen-ai/client-inference.md), [agent spans](https://github.com/open-telemetry/semantic-conventions-genai/blob/e6658f14c9d9ea0760825f029cb82e7673f48fab/docs/gen-ai/gen-ai-agent-spans.md)

Count direct calls once: parent runs must not re-count child-agent work. Separate logical calls from transport retry attempts. Cache-read/write input tokens are subsets of total input; reasoning tokens are part of output. Never add them again. Keep estimated cost separate from billed amounts, with currency and pricing version; the reviewed registry defines no standard cost field. Do not turn sampled spans into an exact billing ledger. [Token accounting](https://github.com/open-telemetry/semantic-conventions-genai/blob/e6658f14c9d9ea0760825f029cb82e7673f48fab/docs/gen-ai/gen-ai-token-metrics.md)

Correlate runs, handoffs, tools, and asynchronous work through existing trace context. Use actual conversation identifiers only when present; do not fabricate them from trace IDs or prompt hashes. Record bounded agent, prompt, model and application versions. Keep run/user/document IDs out of metric labels. Retrieval counts and latency need no document text. Attach existing evaluation results to their operation or response ID, with evaluator/version context; quality evaluation need not be paid or run on every request.

Keep prompts, responses, system instructions, tool arguments/results, retrieval queries and memory content off by default. Current content configuration is `OTEL_INSTRUMENTATION_GENAI_CAPTURE_CONTENT=NO_CONTENT`; verify library support. Review free-text agent descriptions and error messages too. Authorized content capture requires bounded, redacted, access-controlled retention. Required authorization/audit records remain separately governed. [Content capture](https://github.com/open-telemetry/semantic-conventions-genai/blob/e6658f14c9d9ea0760825f029cb82e7673f48fab/docs/gen-ai/gen-ai-spans.md#content-capture-configuration)

Compare p50 and tail latency alongside sample count, time window, outcome mix and workload/version. Measure CPU/GPU/memory only where the workload warrants it. Validate a few emitted success, failure, cancellation and retry paths, including privacy and double-counting. The [November 12 instrumentation experiment](https://opentelemetry.io/blog/2026/agent-harness-genai-instrumentation/) supports public hooks and schema validation; its multi-agent/Kubernetes workflow is not a prerequisite. Reuse local exporters or collectors and test bounded shutdown; do not force a synchronous flush after every server request.
