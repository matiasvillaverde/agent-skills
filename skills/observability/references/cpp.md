# C++ observability and feature verification

Evidence checked 2026-11-13. Inspect the compiler, C++ language mode, standard library, resolved logger/format-library versions, compile definitions, and exception policy. Keep the project's existing logger. The spdlog sources below describe one common backend, not a requirement to add it; confirm features against the pinned dependency. Runtime and sink configuration belong to the executable, and libraries should not silently replace global logging or error policies. [spdlog project](https://github.com/gabime/spdlog), [C++ Core Guidelines](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines)

Record stable operations, terminal outcomes, elapsed time, and bounded error categories at useful boundaries. Avoid per-call/per-iteration records and redundant catch-log-rethrow chains. Use allowlisted contextual fields and a real structured encoder where required, not a string pattern that wraps arbitrary text in JSON quotes. Separate event identity from a human-readable message. Carry correlation with the work when it crosses threads; spdlog's documented thread-local MDC is not supported by its asynchronous mode. Do not assume a worker thread automatically has the caller's context. [spdlog features and MDC](https://github.com/gabime/spdlog), [Sink formatting](https://github.com/gabime/spdlog/wiki/Custom-formatting)

Compile-time and runtime filtering solve different problems. In spdlog, `SPDLOG_ACTIVE_LEVEL` controls compilation of the level macros; direct function calls do not acquire that property. Active macros and ordinary logging functions can still evaluate expensive argument expressions before runtime filtering. Guard expensive preparation with the project's supported level check, preserve source-location needs, and keep logging arguments free of required side effects. A runtime threshold cannot restore statically removed calls. Temporarily enable narrow component diagnostics through the existing configuration rather than adding permanent debug traffic. [spdlog macro implementation](https://github.com/gabime/spdlog/blob/v1.x/include/spdlog/spdlog.h)

Asynchronous logging is not automatically nonblocking or lossless. Define bounded capacity and choose the supported blocking/drop policy deliberately. Inspect drop counters or equivalent evidence, and ensure queued data owns its required storage. In spdlog, the custom thread pool must outlive its loggers; multiple workers may reorder messages. Preserve shutdown ordering and the required final drain. A sink flush is not a universal durability guarantee. Keep audit events distinct from sampled diagnostics with their own actor/action/target/outcome contract, access controls, retention, and explicit delivery failure policy. [spdlog asynchronous logging](https://github.com/gabime/spdlog/wiki/Asynchronous-logging), [OWASP logging](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)

Use the codebase's established exception or error-value model; do not introduce a hierarchy merely for logging. Preserve the originating error and useful operation context. RAII should release resources during failure and cancellation, and destructors must not allow logging failures to escape. Catch where recovery, translation, or a terminal report belongs rather than at every function. Verify ownership of callbacks, captured objects, borrowed strings, and asynchronous operations after a caller stops waiting. A timeout is not proof that underlying work or side effects stopped; cancellation behavior depends on the actual executor/library. Bound outstanding requests and retries using the operation's deadline and idempotency. [Core Guidelines error handling](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#S-errors)

Finish by observing the changed path's normal result and its few relevant malformed-input, dependency, timeout, overload, or cancellation cases. Check one terminal outcome, redaction, request counts, resource cleanup, and queue saturation where changed. Use AddressSanitizer or ThreadSanitizer when memory ownership or races warrant it; their substantial overhead makes them unsuitable as production-performance baselines. Measure optimized builds with representative input and explicit cold/warm distinction, recording elapsed and CPU time. Compare live-allocation growth across repeated completed operations separately from RSS. Profile GPU work only when involved, including completion rather than launch latency. Keep CPU/GPU captures bounded and private, and avoid host-wide perf permission changes. [AddressSanitizer](https://clang.llvm.org/docs/AddressSanitizer.html), [ThreadSanitizer](https://clang.llvm.org/docs/ThreadSanitizer.html), [Benchmark timing](https://google.github.io/benchmark/user_guide.html), [Heap profiling](https://valgrind.org/docs/manual/ms-manual.html), [Linux perf security](https://www.kernel.org/doc/html/latest/admin-guide/perf-security.html)
