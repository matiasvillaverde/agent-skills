# Zig observability and feature verification

Evidence checked 2026-11-13 against Zig 0.17.1 documentation and tagged standard-library source. First identify the project's exact compiler, build mode, target, allocator, I/O runtime, and dependency versions. Check that version's `std.log` and examples before editing: older skill snippets frequently use obsolete build, collection, and I/O APIs. Do not upgrade the toolchain merely to apply this reference. [Versioned language reference](https://ziglang.org/documentation/0.17.1/), [Tagged std.log implementation](https://codeberg.org/ziglang/zig/raw/tag/0.17.1/lib/std/log.zig)

Use existing `std.log` scopes and the application's logging configuration before adding another system. In the reviewed version, levels are error, warning, information, and debug; the default threshold depends on the build mode. An application can supply `std.options.logFn` and scope-level settings. Keep library instrumentation scoped and let the executable choose delivery. Prefer a stable operation name and bounded fields for outcome, elapsed time, and correlation. If the existing sink supports only text, do not describe interpolated text as a structured schema. Use the project's encoder or collector integration when machine-readable fields are actually required. Do not concatenate untrusted input into purported JSON. [std.log](https://codeberg.org/ziglang/zig/raw/tag/0.17.1/lib/std/log.zig)

The reviewed `std.log` performs compile-time level and scope filtering. A custom runtime filter can further restrict the enabled calls, but cannot restore calls removed at compilation. Do not assume a discarded log call makes expensive argument expressions free: guard costly preparation at the call site using the matching supported enablement check. Keep logging expressions free of business side effects. Configure a narrow diagnostic scope for investigation instead of enabling every component. Avoid per-loop records; aggregate counts, timings, and failures at useful boundaries. These are adoption recommendations, not a mandate to build a general-purpose logging abstraction. [std.log source](https://codeberg.org/ziglang/zig/raw/tag/0.17.1/lib/std/log.zig)

The default implementation writes and flushes stderr synchronously and treats write failure as best effort. It is neither a durable audit store nor an asynchronous queue. If measured blocking justifies an asynchronous adapter, define bounded capacity, ownership of queued buffers, drop-versus-backpressure behavior, dropped-record visibility, and shutdown draining. Do not enqueue slices into stack or freed allocation storage. Keep audit events separately identified and governed: actor, action, target, outcome, time, and correlation; exclude secrets and define storage/access/failure policy independently of diagnostic levels. [std.log source](https://codeberg.org/ziglang/zig/raw/tag/0.17.1/lib/std/log.zig), [OWASP logging](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)

Preserve error unions through layers and add operation context at the handling boundary. `defer` handles unconditional cleanup; `errdefer` handles an error return from its enclosing scope. Keep cleanup adjacent to resource acquisition and respect ownership transfer. Avoid scattering catch-and-log behavior throughout the call chain or swallowing failures into plausible defaults. Error integer values are not a stable external taxonomy; use explicitly owned event/error names. Runtime-specific cancellation, timeout, and asynchronous APIs must be checked in the actual project rather than imported from a generic Zig skill. [Errors and cleanup](https://ziglang.org/documentation/0.17.1/#Errors)

After a feature, exercise its normal path and relevant malformed-input, short-I/O, disconnect, deadline, or cancellation behavior. Observe resource release, outstanding operations, bounded request counts, and whether diagnostic failure changes program behavior. Use the project's supported allocator checks for leaks. For performance, record build mode, representative input, cold versus warmed behavior, CPU and elapsed time; investigate live-allocation growth over repeated completed cycles separately from RSS. Use only needed CPU, allocation, or GPU tooling with bounded collection. Keep profiling scoped, protect captures, and do not weaken global perf permissions. [Benchmark measurement controls](https://google.github.io/benchmark/user_guide.html), [Heap profiling](https://valgrind.org/docs/manual/ms-manual.html), [Linux perf security](https://www.kernel.org/doc/html/latest/admin-guide/perf-security.html)
