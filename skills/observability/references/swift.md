# Swift observability and finishing checks

Research checked 2026-11-13. Before editing, inspect the Swift toolchain, deployment targets, Package.resolved, existing logger, and supported SDK availability. Use documentation matching that baseline; do not raise the minimum OS or introduce a logging package to adopt this guidance.

For Apple apps, keep native Logger calls with stable subsystem/category names and small, meaningful events. A subsystem identifies a broad area and a category narrows it. Do not encode user IDs in category names. Preserve native interpolation and privacy annotations instead of building an eager String-based wrapper. Mark only reviewed, nonsensitive values public; numeric values can also be sensitive. Apple’s [Logger documentation](https://developer.apple.com/documentation/os/logger.md) and [logging explanation](https://developer.apple.com/videos/play/wwdc2020/10168/) describe privacy and optimized message handling.

Keep default output quiet. Use the existing app diagnostic controls and native logging configuration for scoped investigations, distinguishing capture settings from Console display filters. Changing a display filter does not reduce emitted work. Prefer one terminal outcome for an operation, with a bounded error code and an existing operation/trace identifier. Record a start only when it helps diagnose unfinished work. Do not treat normal cancellation, a handled retry, or an expected offline condition as a program fault.

For server/shared Swift already using SwiftLog, the executable owns backend bootstrap and verbosity. Libraries must not call bootstrap, replace handlers, or change the host logger’s level. Return or throw failures for the caller to classify rather than logging the same failure at every layer. Swift.org explicitly recommends restrained library levels and useful, bounded debug output. Preserve request metadata through the existing context mechanism; do not add a new task-local logging framework. See [library logging guidance](https://www.swift.org/documentation/server/guides/libraries/log-levels.html) and [LoggingSystem’s one-time bootstrap contract](https://github.com/apple/swift-log/blob/main/Sources/Logging/LoggingSystem.swift).

Close performance intervals on success, failure, and cancellation. Swift cancellation is cooperative: preserve cancellation propagation and cleanup, and stop spawning work when cancellation makes it irrelevant. Bound shutdown of existing asynchronous exporters; the app lifecycle owns it. Do not invent a flush API for Apple’s unified logger. See [Swift concurrency](https://docs.swift.org/swift-book/documentation/the-swift-programming-language/concurrency/).

Use signposts only to answer a timing question. Pair one begin/end using its interval state and unique ID; inspect the resulting Instruments trace. Choose OSSignposter or existing os_signpost according to supported deployment targets. Avoid spans around every function, render, or loop iteration. See [OSSignposter](https://developer.apple.com/documentation/os/ossignposter.md). Rate-limit repetitive diagnostics through existing mechanisms with bounded bookkeeping and visible suppression counts. Required audit records follow their own retention/delivery contract and are not disabled or sampled by a diagnostic verbosity switch; see [OWASP’s distinction between audit and operational logs](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html).

After a feature, exercise its actual UI or service path plus relevant empty/loading states, network failure/timeout, retry, cancellation, and repeated navigation. Confirm the event appears once, correlates correctly, and exposes no sensitive payload. For resource-sensitive changes, compare the same workload before/after in a representative release/profile build. Inspect retained growth after repeated open/close cycles with [Allocations, Leaks, or Memory Graph](https://developer.apple.com/videos/play/wwdc2024/10173/). Use [CPU Profiler where supported, or Time Profiler](https://developer.apple.com/videos/play/wwdc2025/308/); use [Metal tools](https://developer.apple.com/metal/tools/) only for relevant rendering/GPU work. Do not infer a leak from one high memory sample or “no GPU issue” from a CPU trace. Report the measured scenario, baseline, result, and gaps.
