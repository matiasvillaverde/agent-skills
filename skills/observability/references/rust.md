# Rust observability and feature verification

Evidence checked 2026-11-13. Inspect `rust-toolchain.toml`, the actual compiler, `Cargo.lock`, crate features, runtime, and existing subscriber before changing instrumentation. The linked `latest` documentation is a discovery aid; confirm APIs against the versions resolved by this project. Keep an established `log` facade when it meets the requirement. A library emits records; the application owns subscriber/logger initialization, sinks, filters, retention, and shutdown. Do not introduce a parallel framework or install a global subscriber from a reusable library. [Rust log](https://docs.rs/log/latest/log/), [tracing](https://docs.rs/tracing/latest/tracing/)

Instrument a meaningful operation and its terminal outcome, especially external I/O and asynchronous ownership transitions. Use stable event names and explicit fields for outcome, duration, bounded error kind, and correlation. Prefer counts or aggregate timings over per-item events. Request identifiers belong in logs/traces, not unbounded metric labels. Choose levels by operational usefulness; an error event does not automatically justify paging. Select fields explicitly: `instrument` captures arguments by default, so exclude bodies, credentials, headers, and sensitive `Debug` output. Propagate span context across spawned work. Never retain an entered-span guard across an `await`. [tracing](https://docs.rs/tracing/latest/tracing/)

Treat compile-time maximum levels and runtime filters separately. Static level features remove instrumentation; an operator cannot recover it by changing a runtime filter. `EnvFilter` can target particular modules or spans; choose simpler target filtering when adequate. Changes to an environment variable do not magically reload an existing subscriber. If runtime reconfiguration is needed, use the project's supported mechanism and bound its duration. Disabled tracing macros avoid event construction, but a costly summary computed beforehand is already paid for: put necessary preparation behind a matching enabled check. Such checks can differ from a subscriber's more specific filtering, so preserve correctness independently. [Level filters](https://docs.rs/tracing/latest/tracing/level_filters/index.html), [EnvFilter](https://docs.rs/tracing-subscriber/latest/tracing_subscriber/filter/struct.EnvFilter.html), [enabled](https://docs.rs/tracing/latest/tracing/macro.enabled.html)

Make delivery policy explicit. A synchronous sink may block the task. `tracing-appender`'s nonblocking writer has a bounded queue and can drop records; its builder can instead apply backpressure. Retain the worker guard through shutdown, expose its dropped-record count, and decide what saturation means for this workload. Queue acceptance or flushing is not a durable audit acknowledgment. Keep security/business audit events separate from sampled diagnostics, with stable actor/action/target/outcome fields and explicit storage, access, and failure policy. [Nonblocking writer](https://docs.rs/tracing-appender/latest/tracing_appender/non_blocking/), [OWASP logging](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)

Preserve typed errors and source chains while adding useful operation context. Record an error once at the boundary that handles or reports failure; avoid repeating the same source inside both the outer display message and the cause chain. For asynchronous failures, distinguish timeout, cancellation, overload, and dependency error. In Tokio, dropping a join handle detaches its task, while an ordinary timeout does not preempt a future that fails to yield; started blocking tasks cannot be aborted. Verify cleanup and task completion rather than assuming a timed-out caller stopped all work. Bound concurrency and retries by the operation's deadline and idempotency. [Error sources](https://doc.rust-lang.org/std/error/trait.Error.html), [Tokio timeout](https://docs.rs/tokio/latest/tokio/time/fn.timeout.html), [JoinHandle](https://docs.rs/tokio/latest/tokio/task/struct.JoinHandle.html)

Finish with the changed path's normal outcome plus the few relevant timeout, disconnect, cancellation, or overload cases. Inspect emitted records, secret exclusion, duplicate request counts, and eventual task/resource cleanup. Compare optimized builds with matching workload and explicit warmup; distinguish CPU from elapsed time. Check live-allocation growth across repeated completed operations rather than calling one RSS increase a leak. Use bounded, process-scoped profiles, inspect collection overhead, and preserve host restrictions and private artifacts. [Benchmark timing](https://google.github.io/benchmark/user_guide.html), [Heap profiling](https://valgrind.org/docs/manual/ms-manual.html), [Linux perf security](https://www.kernel.org/doc/html/latest/admin-guide/perf-security.html)
