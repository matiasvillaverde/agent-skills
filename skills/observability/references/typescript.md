# TypeScript observability and finishing checks

Research checked 2026-11-13. Inspect the actual runtime (Node, browser, Worker or other), package/lockfile versions, module format, framework hooks, and existing logger/exporters. TypeScript alone supplies no logging lifecycle. Use the runtime’s supported APIs; do not add Pino, OpenTelemetry, a provider, or a platform upgrade merely to follow this reference.

Reuse structured logging already present. Prefer a stable event name, category/component, outcome, duration when useful, and existing request/job/trace ID. Allowlist fields; omit credentials, cookies, full URLs with queries, bodies, raw documents, and arbitrary error objects. Error messages and stacks can contain secrets too. Log a terminal failure at the boundary responsible for handling it, preserving its cause; intermediate layers should enrich and propagate it without another error event.

Let the host own sinks, severity/category controls, redaction, sampling, and lifecycle. A startup LOG_LEVEL environment variable is not a runtime switch. If Pino is already installed, its documented logger.level setter can change verbosity, child bindings carry context, and configured redact paths help protect fields. Validate child/transport threshold behavior for the installed version. Guard expensive debug-only payload construction before doing the work. Do not invent a universal logging wrapper or rely on shallow key redaction for arbitrary nested dumps. See [Pino’s API](https://github.com/pinojs/pino/blob/main/docs/api.md).

Use the existing request context. For Node, AsyncLocalStorage.run scopes context across asynchronous operations and is preferred over enterWith for ordinary request boundaries. Do not put request context in module-global mutable state. Validate inbound correlation identifiers; do not treat them as identity or authorization. Reuse OpenTelemetry propagation where already present instead of inventing trace headers. Node context APIs do not automatically apply to browser/Worker runtimes. See [Node asynchronous context](https://nodejs.org/api/async_context.html).

Libraries emit through the host’s existing API; they do not initialize global SDKs or attach process signal handlers. OpenTelemetry’s [library guidance](https://opentelemetry.io/docs/concepts/instrumentation/libraries/) explicitly separates API from SDK configuration and advises against duplicating underlying instrumentation. Match package versions and ESM/CommonJS setup; [individual instrumentation packages](https://opentelemetry.io/docs/languages/js/libraries/) can avoid an unnecessary metapackage. Keep diagnostic controls distinct from required audit retention and delivery; operational sampling must not drop mandated audit events.

Preserve abort signals and error causes through async work. Perform cleanup in finally, remove event listeners/timers, and classify intentional cancellation separately from unexpected failure. Observe the API’s supported [AbortController semantics](https://nodejs.org/api/globals.html#class-abortcontroller). The application stops new work, drains or cancels outstanding work, then awaits existing exporters/transports within its shutdown budget. Verify the actual flush contract: Pino destination flushing is asynchronous and has runtime/transport limitations; NodeSDK.shutdown returns a promise in the [official implementation](https://github.com/open-telemetry/opentelemetry-js/blob/main/experimental/packages/opentelemetry-sdk-node/src/sdk.ts). Do not force process exit while a flush is pending.

Finish with the changed interaction and relevant failed/slow/offline requests, invalid or empty responses, cancellation, retry, and repeated mount/unmount. Cancellation acknowledgment alone does not prove obsolete results cannot commit: verify a late response cannot update the wrong query, page, or route. Use the [Network panel](https://developer.chrome.com/docs/devtools/network/overview) to inspect counts, initiators, transferred bytes, and requests continuing after navigation. For suspected retained growth, compare repeated cycles and heap snapshots using [Chrome memory tools](https://developer.chrome.com/docs/devtools/memory-problems). Measure renders only when relevant; React [StrictMode](https://react.dev/reference/react/StrictMode) intentionally adds development checks, and [Profiler](https://react.dev/reference/react/Profiler) adds overhead and needs a special production profiling build. Compare like builds/workloads, identify the cause before changing caching or memoization, and report what was measured rather than claiming blanket performance coverage.
