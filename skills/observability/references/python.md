# Python observability and finishing checks

Research checked 2026-11-13. Read the interpreter/version constraint, lockfile, deployment model, and existing logging configuration before editing. Current unversioned Python documentation may describe newer APIs than the project supports. Keep the existing standard logging or structured-logging integration; do not install structlog, an exporter, or upgrade Python solely for this guidance.

Use named module/package loggers with stable event names and small, allowlisted context fields. Include the existing operation/request/trace ID and terminal outcome where it answers a real diagnostic question. Avoid raw request bodies, credentials, cookies, personal data, and arbitrary exception arguments. Preserve an error’s useful type/cause without exposing sensitive payload. Emit the exception once at the boundary that handles or terminates the operation; lower layers normally raise it. Python’s [Logging HOWTO](https://docs.python.org/3/howto/logging.html) distinguishes raising errors from logging suppressed/handled failures.

The executable owns formatting, handlers, output destinations, and runtime category/severity changes. A library should use its own named logger, optionally attach NullHandler, and neither call basicConfig nor configure root handlers behind the application’s back. See [library configuration guidance](https://docs.python.org/3/howto/logging.html#configuring-logging-for-a-library). Check logger and handler thresholds together. Avoid attaching the same destination to both child and ancestor while propagation is enabled: that creates duplicate output. Reconfigure through the application’s supported mechanism; do not invent a remote configuration listener.

Reuse LoggerAdapter, existing structured context, or contextvars as appropriate. Set request-scoped values at the boundary and reset the returned token in finally, so later operations do not inherit stale state. Do not create a logger per request/user or use a global mutable dictionary for concurrent context. Check boundaries involving threads, task creation, and queue workers explicitly. The portable token/reset pattern does not require the context-manager syntax introduced in newer Python versions. See [contextvars](https://docs.python.org/3/library/contextvars.html).

Use lazy logger formatting for ordinary messages, and check isEnabledFor before expensive debug-only computations. Default output should capture meaningful transitions and outcomes, not each loop item or function entry. Bound repeated diagnostic events with existing rate limits/sampling and suppression counts. Keep metric labels bounded. Required audit events retain their independent delivery, retention, and failure policy; disabling debug or sampling request logs must not disable them. See [OWASP logging guidance](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html).

Blocking file/network handlers can stall asyncio. If this is demonstrated or already addressed, preserve the application’s QueueHandler/QueueListener arrangement instead of adding a second queue. Bound capacity and define overflow behavior: QueueHandler can drop a record when enqueueing fails. Stop producers and drain/stop listeners before closing handlers; listener.stop waits and is not inherently a timeout API. Ensure the existing shutdown design accounts for stalled sinks and queue saturation. See [Logging Cookbook](https://docs.python.org/3/howto/logging-cookbook.html) and [handler contracts](https://docs.python.org/3/library/logging.handlers.html). Propagate CancelledError after cleanup; swallowing it can break TaskGroup and timeout behavior. See [task cancellation](https://docs.python.org/3/library/asyncio-task.html#task-cancellation).

Finish by exercising the changed path and relevant timeout, unavailable dependency, malformed/empty input, cancellation, and retry-exhaustion behavior. Check that background tasks, connections, and handlers close after repeated runs, and one failure produces one useful terminal report. For CPU concerns, profile the representative workload with the project-supported [Python profiler](https://docs.python.org/3/library/profile.html). For suspected retained Python allocations, compare [tracemalloc snapshots](https://docs.python.org/3/library/tracemalloc.html) across equivalent repeated cycles; this alone does not account for every native/GPU allocation. Record request counts, timing and resource evidence where relevant. Add a focused regression test only for a credible gap, not a matrix for every severity or log message.
