# Research, Mobbin and five-way comparison

Read when exploring a new visual direction. Reuse recent relevant evidence during refinement;
refresh it when a new task, platform change or contradictory observation affects the choice.

## Research the task before choosing a look

Inspect the existing screen or its entry points, real content, supported states and components.
Separate working behavior from proposed additions. Identify whether the main job is operating
a tool, reading content or making a decision; density, typography and hierarchy follow that job.
Use the current brand, including licensed fonts and assets, unless changing it was requested.

Use Mobbin MCP when available for shipped-product inspiration, plus current official platform
guidance and firsthand comparable products. Search the actual job and screen, not only a style
word. Start with a small relevant set; follow a result with another query when it exposes an
unanswered question. For example, a library screen may reveal a need to inspect the save/recovery
flow. Stop when the important alternatives and constraints are supported, not at an image quota.

For each reference retained, capture **link, platform/date if known, observed pattern, relevance,
tradeoff and intended adaptation**. Include a counterexample when it changes the decision.
Familiar products and repeated patterns are useful evidence, not proof of conversion, usability
or accessibility. Attribute measured outcomes only when the source actually reports them.

## Use the actual Mobbin tool contract

Discover exposed tools and their schemas rather than copying an old unofficial integration.
The [official feature guide](https://docs.mobbin.com/mcp/features) separates:

- `search_screens`: one screen and its meaningful state.
- `search_flows`: one journey, such as saving an article or recovering a failed payment.
- `search_sections`: a website section, such as a comparison or pricing section.
- Collection read tools: use an existing collection when the task identifies it. Saving,
  creating collections or posting comments is a separate external action, not needed for research.

At the 2026-11-15 check, screen/flow search supports `ios` and `web`; never invent a `macos`
or `android` parameter. Where native coverage is absent, use official resources and directly
observed native products; label any cross-platform inspiration. Check the current schema again
when using it. Use one plain-language intent per query, with product category when relevant.
Keep `task_intent` and output destination consistent through a task and free of private context.

**Inspect the returned images before describing them.** A partial match can inform a pattern
without being a suitable reference for the whole feature. Refine or exclude it deliberately.
Flow results may contain only spaced previews: establish which steps you saw, and do not infer
unseen transitions, persistence, animation, keyboard behavior or accessibility from stills.

Cite each mentioned reference with its returned canonical `mobbin_url`. Inline previews are for
inspection; when the requested artifact embeds or saves a reference, download its high-resolution
`image_url` into the task's approved asset area and retain its citation. Do not use expiring image
URLs as durable citations. Preserve any tool-required usage notice verbatim. Use patterns as
inspiration, not another product's brand, proprietary illustrations or copy as shipped assets.

If access is missing, say what could not be inspected, use available official/product references
and label the limitation. Do not claim a Mobbin search happened or silently install another server.

## Make five genuinely different, comparable proposals

Before rendering, describe each candidate's structural idea and why it helps the same user job.
Use more than cosmetic variation: information hierarchy, navigation/placement, grouping/density,
type roles, editorial emphasis or interaction model where in scope. Across the set, explore more
than one meaningful axis. Five colors or five fonts on the same layout do not satisfy this request.
Do not create a deliberately bad fifth option or add features merely to make it different.

Hold data, representative content, main task and comparison state constant. Preserve fixed
chrome and areas outside the brief. Show a key interaction/state when it distinguishes the design;
avoid a combinatorial board for every theme, screen and state. Mark mock data and proposed behavior.
Use numbers that remain stable through refinement. A selected direction can combine named parts.

Use the requested canvas/prototype tool when it is available. Otherwise make a local, inspectable
HTML or native preview suited to the platform. Do not change a router, install a design framework,
launch five agents or publish a site just to generate alternatives. A visual request needs visible
mockups, not five prose names. Explain if rendering is unavailable and distinguish specs from previews.

Read back or open the actual artifact. Check all five render, their labels match the comparison,
shared content is consistent, and text/assets fit. For interactive prototypes, exercise the primary
action and relevant recovery state. Check representative window/viewport sizes and text scaling,
focus/keyboard or touch behavior appropriate to the target. An HTML approximation of iOS is design
evidence, not proof that the native component works or meets VoiceOver requirements.

Recommend using task clarity, brand coherence, native conventions, accessibility and implementation
cost. Explain the tradeoff in ordinary language. Preserve earlier rounds and the final design decision;
remove only task-owned temporary downloads/builds after useful artifacts and citations are retained.
